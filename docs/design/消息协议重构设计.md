# 消息协议重构设计（WS 实时流）- 全路径版

> 独立 HTTP 服务（server-entry）体系的会话实时消息协议重设计。
> 目标：单一统一事件流，消除全量 snapshot 的重复推送与冗余消息，
> 让"一条命令"对应确定且最少的 WS 消息。
> 本文为变更设计说明，原 `docs/design/结构设计.md` 保持为基线文档，本设计落地后回填基线。
> **全路径清单在 §3**：穷举所有触发场景与消息序列，防止重构遗漏边界。

## 1. 现状问题分析

### 1.1 一条命令当前产生的消息（web 视角）

```
web ──exec──▶ server ──run-exec──▶ agent ──exec──▶ session(PTY)
      ◀─sessions(busy:true)   （exec 触发）
      ◀─cmdStart(command)      （agent 首块 stream 带 command）
      ◀─run(data)…             （输出增量）
      ◀─sessions(busy:false)   （agent done #1 → server 广播）
      ◀─runEnd                  （buf.done 转变）
      ◀─sessions(busy:false)   （agent done #2 转变检测 → server 又广播）
      ◀─snapshot(pairs 全量)    （forceSnap 后 server 重建全量历史）
```

### 1.2 问题清单

| # | 问题 | 根因 |
|---|---|---|
| P1 | 命令完成触发**全量 snapshot**（pairs 重复推送，历史越长越大） | server 用 snapshot 表达"历史新增一条"，web 整块重渲染 |
| P2 | `runEnd` 是冗余消息（web 端直接忽略，注释"等待后续 snapshot"） | 既有 runEnd 又发 snapshot，语义重叠 |
| P3 | `busy:false` 的 `sessions` 出现两次 | agent 在 `run-exec.finally` 与 `pushStreams` 转变检测**各发一次 done**，server 每次 done 都广播 sessions |
| P4 | `runEnd` 不总在最后 / 消息顺序语义混乱 | 命令完成同时触发 sessions 广播、runEnd、forceSnap 三条路径，彼此时序不保证 |
| P5 | `stream` 消息被复用表达三件事（数据增量 / command 开始 / done 完成） | agent pushStreams 用 `command` 字段 + `done` 字段重载 |
| P6 | `raw` 与 transcript 两套并行数据缓冲、两套游标状态（_bufPos/_rawPos/_sentDone/_forceSnap…），客户端状态机复杂 | 两种模式共用订阅生命周期，server 维护 6 个 per-client 字段 |
| P7 | server 保留同进程 session 直连分支（`entry.session.exec` / `getRunningStream`），与 agent 路径并存 | 独立模式 `getSessions()` 恒空，直连分支实际死代码，却占用了复杂度与分支 |
| P8 | server 从"推送命令"推导命令开始（stream{command}），插件自身 exec 的命令开始时序不统一 | 命令开始/结束没有单一显式事件源 |

## 2. 目标协议设计

### 2.1 原则

1. **每种消息只做一件事**；命令生命周期与输出增量分离。
2. **snapshot 只在订阅/切回 transcript 时发送一次**，作为基线；之后全部走增量 diff。
3. **busy 是会话属性**，随 `sessions` 推送，状态翻转时按 json 去重广播一次。
4. web 端**本地累积**命令/输出对，渲染完全由本地 pairs 驱动，不依赖逐命令 snapshot。
5. raw 与 transcript 是**同一订阅下的模式切换**（`setMode`），不改变订阅生命周期。
6. **server 只认 agent 上报**；命令生命周期（cmdStart/cmdDone）与输出（out）均由 agent 统一产出，web-exec 与插件-exec（term_cli）两条来源共用同一上报通道。删除同进程 session 直连分支（死代码）。
7. **命令生命周期由 BaseSession 生命周期钩子精确上报**（`setLifecycle`）：命令开始（`_beginCapture`）发 `cmdStart`，完成（exec done/interactive、后台 watch 完成）发 `cmdDone`，每命令各恰好一次、幂等。不用 pushStreams 轮询转变检测——`exec()` 同步等待命令结束后才返回，快速命令（生命周期落在单个 100ms tick 内）轮询会漏报导致 server busy 卡死。
8. **send/exec 决策在 agent 端**：web 输入框统一发 `exec`（提交意图），agent 用 `session.hasRunningStream()` 实时判断——忙/交互→原样 `send`，空闲→`exec`。避免 web 基于有推送延迟的 busy/connected 误判。

### 2.2 消息总表

#### A. Web → Server（客户端请求）

| type | 字段 | 含义 |
|---|---|---|
| `list` | - | 请求会话列表（服务端回 `sessions`） |
| `subscribe` | `sessionID,name` | 订阅某终端：服务端回一次 `snapshot`（基线） |
| `unsubscribe` | - | 取消订阅 |
| `setMode` | `mode:"transcript"\|"raw"` | 切换南面通道；*不重新订阅*。transcript→raw 停推 diff、补 raw 全量+meta；raw→transcript 停推 raw、回补一次 `snapshot` |
| `exec` | `sessionID,name,command` | 执行命令（转发 agent，run-exec） |
| `send` | `sessionID,name,text` | 发送文本/按键（转发 agent，run-send） |
| `deleteTerminal` | `sessionID,name` | 删除终端（仅已断开终端） |

#### B. Agent → Server（数据源，唯一事实来源）

| type | 字段 | 含义 |
|---|---|---|
| `register` | `sessions[]` | 注册本插件进程持有的会话（连接建立/会话增删时 reRegister） |
| `cmdStart` | `sessionID,name,command,ts` | 某命令开始（**生命周期监听器**：BaseSession._beginCapture 精确发出，含插件自身 exec） |
| `out` | `sessionID,name,data` | 命令输出增量（tick 推流，append 到 server 侧 buffer） |
| `cmdDone` | `sessionID,name,exitCode,endTs` | 某命令完成/中断/交互退出（**生命周期监听器**：exec done/interactive/watch 完成点精确发出，每命令恰好一次） |
| `raw` | `sessionID,name,data,pos,reset` | 原始字节流（raw 通道，与 transcript 并行） |

> agent 侧机制（**实现修正**）：命令生命周期事件由 `BaseSession.setLifecycle()` 挂接的监听器在
> 命令**开始（_beginCapture）与完成（exec done/interactive、后台 watch 完成）时精确发出**，
> 而非 pushStreams 轮询转变检测。原因：`exec()` 同步等待命令结束后才返回，快速命令
> （生命周期落在单个 100ms tick 内）轮询检测会漏报，导致 server 端 busy 卡死。
> 生命周期钩子对 web-exec（run-exec）与插件自身 exec（term_cli）**两条来源天然统一**。
> pushStreams 仅负责 out 增量与 raw 增量推流。
> `run-exec` 成功路径不再补发 done；仅 quick-fail（{ok:false}：busy/未连接）与异常时补发 cmdDone 兜底（server 幂等）。

#### C. Server → Web（客户端视图）

| type | 字段 | 含义 |
|---|---|---|
| `sessions` | `sessions[]`（含 busy/connected） | 会话列表与状态；busy 翻转即刻推，其余按 json 变化去重（statusTimer 2s 兜底） |
| `snapshot` | `sessionID,name,pairs[]` | 全量历史基线；仅 `subscribe`、raw→transcript 切回时发送。运行中命令以 `cmd`+`run` 对并入 |
| `diff` | `sessionID,name,event,command?,data?,exitCode?,endTs?,ts?` | 增量事件：`event:"cmd"` 新命令（转发行 cmdStart）\| `event:"out"` 输出追加（转发行 out）\| `event:"done"` 当前命令完成（转发行 cmdDone） |
| `meta` | `sessionID,name,commands` | 轻量命令计数（raw 模式用；cmdDone 时 +1） |
| `raw` | `sessionID,name,data,pos,reset` | 原始字节流（raw 模式用，转发行 raw） |

**废弃**：`run`、`runEnd`、`cmdStart`（web 向）、`done`/`result`（agent 向）、`stream`（agent 向）。
全部由 `diff` 事件、`cmdStart`/`cmdDone`（agent 向）取代。

### 2.3 一条命令的目标消息序列（web 发起，transcript 模式）

```
        web                 server                agent
exec ─────────────────▶
        ◀──sessions(busy:true)      ◀──cmdStart(command,ts)   ← 生命周期钩子 _beginCapture
        ◀──diff{event:"cmd",command,ts}
        ◀──diff{event:"out",data}…  ◀──out(data)…             ← tick 推流
        ◀──sessions(busy:false)     ◀──cmdDone(exitCode,endTs) ← 生命周期钩子命令完成，唯一一次
        ◀──diff{event:"done",exitCode,endTs}
```

- snapshot **不出现**（历史由 web 本地累积）；runEnd **不出现**。
- `sessions` 正常路径恰好两次（busy:true → busy:false），由 json 去重天然保证
  （执行中也是 busy:true，故忙碌期多次 sessions 推送会被去重）。**异常路径例外**：
  交互程序（sudo/read 等待输入）busy 保持直到 marker 出现，期间只推一次 busy:true（C4）。
- diff 事件按发送顺序到达，web 按序累积，"done 在最后"语义天然成立。

### 2.4 订阅与模式切换

```
connect → list → sessions
        → subscribe → snapshot(基线) + (mode=transcript 默认)

mode=raw：       setMode{raw} → server 停发 diff，发 raw全量(reset)+meta
                （raw 期间命令仍由 agent→server 正常流转，只是不向该客户端发 diff）
mode=transcript：setMode{transcript} → server 回补 snapshot(最新基线) + 恢复 diff

执行中切换 raw→transcript：snapshot 将包含运行中命令的已输出部分 + run 对。
```

### 2.5 Server 侧状态（大幅简化）

| 状态 | 用途 |
|---|---|
| `streamBuf.(sessionKey)` `{data, done, ts, command}` | transcript 通道当前命令缓冲 + 完成标志（busy 推导、晚订阅者基线）；`done` 由 `cmdDone` 置位 |
| `lastOutTs.(sessionKey)` | 最近一次 out 到达时刻（BUSY_TIMEOUT 兜底：超时未 cmdDone 视为完成） |
| `rawBuf.(sessionKey)` `{data, pos}` | raw 通道字节缓冲（reset 时替换） |
| `cmdCount.(sessionKey)` | 已完成的命令计数（cmdDone 时 +1，meta 提供） |
| `agentBySession` | agent→会话归属（消息路由） |
| per-client：`_sub, _mode, _txPos` | 订阅目标、模式、命令输出已推送字节偏移。`_txPos` 用途：晚订阅者订阅时对齐到 streamBuf 当前长度（快照基线已含运行中输出），此后 out 仅推 `slice(_txPos)` 增量，避免快照 run 对与后续 out 重复（C1） |

**删除**：`_sentDone`、`_forceSnap`、`_snapBase`、`_wasRunning`、`_lastKey`、`_lastSessionsJson` 的强制覆盖逻辑。
`_bufPos` **改名保留**为 `_txPos`（不是删除）：每条命令开始时重置为 0，subscribe/重建基线时对齐当前 buf 长度。
`_rawPos` 删除：raw 通道 agent 每 tick 推的已是增量且 WS 保序，server 收到 `raw` 消息直接转发给该会话的 raw 订阅者，不再做 per-client 第二道切片（C2）。
聚合推送 `sessions` 仅依赖 json 本身变化判断，不再手动垫 `_lastSessionsJson`。

### 2.6 Web 端渲染

- `localPairs: TranscriptPair[]`：订阅时由 `snapshot` 填充，之后：
- `diff{event:"cmd"}` → push `{type:"cmd",text:command,ts}`、置 pending
   - `diff{event:"out"}` → 打开/续写当前输出块（TermScreen 实时渲染）；**无 pending 块时**（D1 交互路径 cmdDone 已固化）追加到最后一个已固化 out 块的 live 区（C5）
   - `diff{event:"done"}` → 为当前输出块补 exitCode/endTs，固化 pending
- transcript / raw 两种视图分别由 `localPairs` 与 raw 通道渲染，互不污染。
- 刷新/重连 → 重新 connect + subscribe → snapshot 基线恢复。

### 2.7 关键决策（已落地，随实现修正）

| # | 事项 | 最终决策 | 落地说明 |
|---|---|---|---|
| D1 | 交互程序（sudo/read/top/REPL）的 busy 与完成判定 | **统一追加完成 marker；交互期间保留 running 上下文、busy=true**，由后台 watch 持续监听 marker；`INTERACTIVE_RE`（sudo 密码/确认提示）仅用于 prompt 立即返回 interactive（不等 5s 动画窗口） | 修法：`exec` interactive 分支不再 `_clearRunningContext`/`busy=false`，改转 `_startBackgroundWatch`；marker 出现（含用户 send 输入后）→ 完整收集输出 + `_emitDone` + busy=false。实测 `top`/`read`/`python` 退出后 marker 均正常输出 |
| D2 | 前台返回型 vs REPL stdin 型 | **不再区分**：`INTERACTIVE_PROGRAMS` 名单移除，所有命令统一追加 marker | 旧注释"REPL 型不吃追加行"基于独立行追加的旧实现；当前 `;` 同一行拼接是 shell 命令行层解析，`python; printf ...` 中 printf 由 shell 在 python 退出后执行，不会被 REPL 当 stdin 消费（已实测） |
| D3 | send/exec 决策放在哪 | **移到 agent 端**：web 输入框统一发 `exec`；agent 收到 run-exec 用 `session.hasRunningStream()` 实时判断——忙/交互→`send` 原样发，空闲→`exec` | web 的 busy/connected 来自 server 2s 推送有延迟，易误判（忙时走 send 命令真实执行但无 marker 不进 transcript） |
| D4 | busy 兜底 | **仅 agent 连接消失才清 busy**，不用"无 out 超时" | 交互命令等待输入时无输出，30s 无 out 判定会把交互误判为僵尸；agent 生命周期钩子（含 watch 超时发 done）已兜底正常命令。`lastOutTs`/`BUSY_TIMEOUT` 移除 |
| D5 | 交互程序完成恢复 | watch 超时（MAX_WATCH_LEN）/ 断连补发 `done`，busy 恢复 | 交互程序 marker 出现即完成；极端情况（REPL 长期不退出）由 watch 超时兜底 |

## 3. 全路径清单

> 穷举所有触发场景。每表 = 触发源 + 消息传播 + 目标方案行为 + 边界说明。
> 标注 **覆盖**=目标协议已天然处理；**处理**=需实现时编写；**保留现状**=行为不变，仅换消息名。

### 3.1 连接与订阅

| # | 场景 | 传播路径（目标方案） | 边界/备注 |
|---|---|---|---|
| F1 | Web 初始加载 | `connect → list → sessions`（首次 2s 内 statusTimer） | 页面无会话时下拉空，subscribe 不发出（web 侧无 sid）——保留现状，**覆盖** |
| F2 | 订阅 transcript | `subscribe → snapshot(基线)`；随后 diff 增量 | 基线含运行中命令的 `cmd`+`run` 对，**处理** |
| F3 | 订阅 raw | `subscribe → meta(命令数) + raw全量(reset)` | 同 setMode{raw}，**覆盖**（复用现有逻辑） |
| F4 | 订阅不存在的会话 | `subscribe → snapshot{notFound}` → web dropDeadTerminal | 保留现状，**覆盖** |
| F5 | 切换会话/终端下拉 | 本地清 subSid/subName → `subscribe`（重订阅，仅当选中的会话/终端实际变化） | 目前 web 已有变化检测，**覆盖** |
| F6 | 断线 | 页面提示刷新，不自动重连 | 保留现状，**覆盖** |
| F7 | unsubscribe | 清理 _sub/_mode；server 对该客户停发 diff/raw | 现有仅 _sub=undefined；补 _mode 清理，**处理** |

### 3.2 命令执行（transcript 模式）

| # | 场景 | 传播路径（目标方案） | 边界/备注 |
|---|---|---|---|
| F8 | web 发起普通命令 | `exec → run-exec → (agent) cmdStart → out×N → cmdDone → sessions(busy:true/false) → diff{cmd/out…/done}` | §2.3，**覆盖** |
| F9 | 插件自身 exec（term_cli exec，不经 web） | 同一上报通道：BaseSession 生命周期钩子 `cmdStart → out×N → cmdDone`（前提：web 已订阅该会话） | **覆盖**（生命周期钩子对两条 exec 来源天然统一） |
| F10 | 命令输出动画/长运行（apt 下载、进度条） | `cmdStart → out×N` 持续；busy 保持 true；直到 cmdDone | 长命令 marker 出现即完成，**覆盖** |
| F11 | 命令失败退出（非 0） | 同 F8，`cmdDone(exitCode=N)` → `diff{done,exitCode=N}`，web 时间列红✗ | **覆盖** |
| F12 | Ctrl-C 中断 | session 侧 detectInterrupt 判 ^C → 命令结束，生命周期钩子 `cmdDone(exitCode=130)`；同时 shell 继续执行追加的 `;printf` 也会出 marker（二者幂等，server 去重） | **覆盖** |
| F13 | 交互程序（sudo 密码 / read / top / REPL） | **统一追加 marker**：进入交互后保留 running 上下文、busy=true，转后台 watch 监听 marker；`INTERACTIVE_RE` 命中即返回 interactive（不等 5s 动画窗口）；用户 send 输入后命令完成 → marker → 完整收集 + cmdDone + busy=false | **已落地**（见 D1/D2） |
| F14 | busy 时 web Send（子 shell 内按键） | `send → run-send`，无生命周期事件；输出经 out 通道回流 | **覆盖** |
| F15 | 命令执行中发起第二条命令 | agent 用 `hasRunningStream()` 判断：忙/交互→原样 `send`（不产生新命令），空闲→`exec` | **已落地**（D3） |

### 3.3 模式切换与 raw

| # | 场景 | 传播路径（目标方案） | 边界/备注 |
|---|---|---|---|

### 3.4 会话生命周期

| # | 场景 | 传播路径（目标方案） | 边界/备注 |
|---|---|---|---|
| F20 | 删除已断开终端（web×） | `deleteTerminal → server removeSessionState + 若可发 run-delete(agent close) → sessions 广播`；web 本地先删下拉项 | 仅允许断开终端（web 已强制），**覆盖**；注意 server 侧删除后 session 状态文件移除，next sessions 不含有 |
| F21 | opencode 会话删除（session.deleted） | cleanAllSessions → removeAllSessionStates + reRegister(空) → next sessions 不含该会话；web 订阅若仍指向它 → 下次 snapshot 访问时 notFound → dropDeadTerminal | **覆盖** |
| F22 | 会话断开/连接失败（ssh 断线） | agent 侧 session state 断开 → reRegister/next sessions `connected:false`；streamBuf 若有残留运行时 → cmdDone 兜底 | **覆盖** |
| F23 | 会话中途消失但仍订阅 | 同 F4：snapshot{notFound} 或 sessions 里找不到 → web 清理 | **覆盖** |
| F24 | agent 断连兜底（防 busy 卡死） | server 仅当 `agentBySession` 不含该 key（agent 连接消失）时清 busy + 广播 cmdDone | **已落地**（D4）；不用"无 out 超时"——交互命令等待输入时无输出但 agent 仍在 |
| F25 | 最大历史对数修剪（maxMessages） | SessionHistory 内部 trim 最旧文件；snapshot 重取时自然反映 | **覆盖** |
| F26 | 历史缓存清理（会话 close dispose） | 无关消息流，web 下次 snapshot 读不到历史 → notFound | **覆盖** |

### 3.5 进程与服务生命周期

| # | 场景 | 传播路径（目标方案） | 边界/备注 |
|---|---|---|---|
| F27 | agent 首次连接独立服务 | `register(sessions)` → agentBySession 建立 | **覆盖** |
| F28 | 会话增删后 reRegister | `reRegister(sessions)` 增量覆盖 agentBySession | **覆盖** |
| F29 | agent 断线重连（2s） | 重连→register→对运行中命令补发 cmdStart+out(剩余)+raw全量(reset) | **处理**：首轮 full 补发 |
| F30 | 服务重启/版本升级（proto 不符 killStale） | 独立服务旧进程被杀 → 新进程 streamBuf/rawBuf 空 → 各 agent 需重连（F29）；web 断线提示刷新 | **处理**：proto 机制保留 |
| F31 | 服务空闲自动关闭（idleShutdownMs） | 同上，服务退出 web 断线，agent 2s 重连→服务已死→持续重连（现状即此） | **保留现状** |

### 3.6 竞争与干扰（重构重点防遗漏）

| # | 场景 | 现状缺陷 | 目标方案行为 |
|---|---|---|---|
| F32 | 命令开始与 echo 数据分属两个 tick | stream{command} 推 cmdStart 时可能漏掉同 tick 数据 | cmdStart/out 均由 agent 顺序发出，server 在本连接内按收到的顺序转发 diff，天然有序 |
| F33 | 命令 A 完成随即命令 B 开始 | 需保证 A 的 cmdDone 与 B 的 cmdStart 均发出 | 生命周期钩子在命令边界精确发出：A 完成 `done`、B 开始 `start`，天然各一次、顺序由 BaseSession 执行序保证，无轮询竞态（实现修正） |
| F34 | 两个客户端订阅同一终端（通常同源） | 各自 _bufPos 独立，快慢客户端互不影响 | 运行中命令的 out 增量按各订阅者 `_txPos` 切片（快慢不互扰），已固化命令的 diff{cmd/done} 广播一致；事件顺序各订阅者一致（WS FIFO）（C3） |
| F35 | exec 广播 sessions 与 statusTimer sessions 竞态 | 手动垫 _lastSessionsJson 导致强制推、状态洪泛 | busy 翻转即刻推 + json 去重兜底；不再垫字段，幂等 |
| F36 | raw 客户端与 transcript 客户端并存订同一终端 | raw 推流与 snapshot/run 并存，_clean 逻辑复杂 | 各客户端 _mode 独立；transcript 订阅者只见 diff，raw 订阅者只见 raw+meta，互不干扰 |
| F37 | snapshot 与 diff 乱序（快慢网络） | forceSnap 与增量并存 | snapshot 仅在连接建立/模式切换时发，之后纯 diff；同一 WS 通道 FIFO，顺序天然一致 |
| F38 | web 下拉未变时 sessions 推送触发 updateTerminalSelect 重订阅 | 现状已修（仅当选中的会话/终端实际变化时重订阅） | 保留现状 | 
| F39 | 命令完成瞬间 history 尚未落盘（agent 未 append） | 现状 snapshot 依赖落盘历史 | cmdDone 由 agent 在 exec 返回**之后**发出（history 已 append），server 端 diff{done} 不依赖文件，web 本地 blocks 已含输出，无需文件时序 |
| F40 | **连续输入时 marker 检测失败 → busy 卡死** | `extractOutputStart` 的 `findLastEndOf`（全局最后匹配）被后续 send 的裸命令回显带偏到 marker 之后；`detectLastDoneMarker` 从该错位 echoEnd 搜索 → 永远找不到当前命令 marker → 卡 running | 修复：**marker 检测改为从命令起点搜索**（marker 带唯一 seq，天然免疫旧残留与回显错位）；echo 定位 `extractOutputStart` 增加 `endBound` 参数，限制在 marker 之前取最后匹配（`findLastEndOfBefore`）。涉及 `_extractOutput`/`getRunningStream`/`_waitCompletion`/`_startBackgroundWatch`/`readBuffer` |

## 5. 风险与回退

| 风险 | 影响 | 缓解 |
|---|---|---|
| 晚订阅者需包含运行中命令 | 基线缺运行中输出 | snapshot 组装时把 streamBuf 当前命令转为 `cmd`+`run` 对（沿用现状逻辑） |
| agent 端命令由非 web 来源触发（插件自身 exec） | diff 仍应广播给所有订阅者 | cmdStart/out/cmdDone 由 BaseSession 生命周期钩子统一上报，web 不区分来源，天然覆盖 |
| 快速命令漏报生命周期（轮询检测测不出） | server busy 卡死 | **实现修正**：生命周期钩子精确挂在命令开始/完成点，不依赖轮询（见 §3 B 表注） |
| 模式切换时序（切换瞬间的命令） | transcript/raw 画面短暂不一致 | 切换时以 snapshot(transcript) / raw全量(reset) 重建基线，可接受 |
| 交互程序 REPL 长期不退出 | busy 长期 true、web 无法执行新命令 | 符合真实语义（终端被占用）；watch 超时（MAX_WATCH_LEN）兜底发 done 恢复 |
| agent 与服务双进程升级错配 | 消息不兼容 | 协议版本 SERVER_PROTO_VERSION 递增（当前 4），ensureServer 版本校验杀旧重启（机制保留） |
